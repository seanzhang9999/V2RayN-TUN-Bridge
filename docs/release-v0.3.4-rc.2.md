## Windows 出站保护与 DHCP 续租

上一版在全机保护开启时可能遇到 Wi-Fi 已连接、应用却全部断网的情况。一次现场故障中，Windows 先报告 DHCP 续租失败，随后 TUN 丢失默认物理接口。此时控制台仍有响应，两个独立站点均无法完成 TLS 握手。手动切换 Wi-Fi 发生在故障之后。

本版在 Windows Filtering Platform 中为 DHCP 客户端增加物理出站规则。规则同时匹配系统 svchost.exe 路径、DHCP 服务身份、物理接口及 UDP 端口对。IPv4 使用本地 68 到服务器 67，IPv6 使用本地 546 到服务器 547。即使接口尚未获得地址，Bridge 也能发现物理网卡。其他应用继续受原有物理出站策略约束。

普通 IPv4 应用和 SSH 进入 Mihomo TUN，经本机 1081 交给 v2rayN 的 Xray 分流。Xray 的物理出站继续受 VPN 节点和直连地址白名单约束。系统代理应用也可以直接使用 1081。局域网和热点登录保留各自的接口级例外。[网络拓扑、DNS 和停用步骤](https://github.com/seanzhang9999/V2RayN-TUN-Bridge/blob/v0.3.4-rc.2/README.zh-CN.md)

解压 Windows x64 附件后运行 `guard-console.pyw`，需要 64 位 Python 3.11+（含 Tk）及已运行的 v2rayN/Xray。

## 验证范围

在手机热点上同时开启保护和 TUN 后，物理网卡记录到 DHCP 请求与服务器回复，Windows 确认租约到期时间延后。IPv4 和 IPv6 的物理出站阻断规则均已核实。该热点没有公网 IPv6 默认路由。睡眠唤醒、跨热点连续运行及 Antigravity 重新授权仍待独立验证。

一次连续 30 分钟的 Windows 实测中，91 次 HTTPS 检查、两台 SSH 主机各 7 次新会话认证、4 次已登录 Codex 请求均成功，31 次控制台采样均有响应。热点在观察期间自动续租成功。物理 Wi-Fi 的 189,130 个出站 IPv4 包中，97,736 个发往 VPN 节点，91,393 个发往直连白名单，1 个为向热点 DHCP 服务器续租。未观察到白名单以外的公网目标。Antigravity 保留了已有会话。

**已知问题。** 上述观察结束后，同机再次出现代理与直连中断。TUN 日志记录了 UDP 请求解析超时，用户报告停止 TUN 后仍无法连接，关闭出站保护后有所恢复，手机热点随后也重新联网。第二次事件没有同期物理网卡抓包，确切原因仍待确认。本次发布保留预发布标记。

后续核对发现，该机 v2rayN 的 1081 入站关闭了 UDP。对运行中的监听器执行 SOCKS5 UDP ASSOCIATE，实测返回 7（不支持该命令）。这可以解释 UDP 转发受限。故障期间两个不同站点的 UDP 访问另有 DNS 解析超时记录，整机断流与热点侧的关系仍待确认。
