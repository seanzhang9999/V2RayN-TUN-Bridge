## 二、P0-1：直连规则带 domain 就整条丢弃（解释「直连不通」）

```python
# xray_direct.py:115（基线）
def direct_networks(path):
    for _, rule in direct_rules(path):
        if set(rule) - {'type','outboundTag','ip'} or rule.get('type') != 'field':
            continue              # ← 规则里有 domain 字段，整条丢掉，连 ip 部分也不采信
```

```python
# guard_live.py:187-197
add('physical egress', g['BLOCK'], 1, [])              # 默认全阻断
for network in networks:
    g['permit_network'](handle, sub, app, network)     # 只有这些网段开口
```

v2rayN 的直连规则常见形态是 `{domain: ["geosite:cn"], ip: ["geoip:cn"]}` 或纯 `domain`。前者键集合非空 → `continue`；后者连 `ip` 都没有。两种情况下 WFP 都拿不到任何直连放行，于是 Xray 决定 direct 后建的物理 socket 被默认规则**静默丢弃**——用户看到的就是「开保护之后直连全不通」，而代理与 TUN 本身是好的。

这也解释了「有时能用、有时不能用」：只有当路由里存在**纯 IP** 形态的直连规则（`ip` 里写死 CIDR 或 `geoip:cn`，且不含 domain）时才被采信。

### 已实施的修复

`xray_direct.py` 新增 `direct_items(rule)`，按「这条规则是否只由目标条件构成」判断，而不是按键集合白名单：

```python
DESTINATION_KEYS = frozenset({'type', 'outboundTag', 'ip', 'domain', 'port', 'network'})

def direct_items(rule):
    if rule.get('type', 'field') != 'field':
        return ()
    if set(rule) - DESTINATION_KEYS:
        return ()
    items = rule.get('ip')
    return tuple(items) if isinstance(items, list) else ()
```

要点：

- `domain` 与 `ip` 同在一条规则里，Xray 对同一字段取并集、对不同字段取交集，因此该规则仍然把这些 IP 判为直连 → `ip` 部分必须采信。
- `type` 缺省视为 `field`（Xray 的默认值），旧代码要求显式出现 `type` 键。
- `source` / `inboundTag` / `user` / `protocol` / `attributes` 一律不转换：那是把「条件放行」放大成「无条件放行」，用阻断换泄露，不划算。
- `0.0.0.0/0`、`geoip:private` 之类既不展开也不报错，保持原行为。

回归测试：`tests/test_xray_direct.py`，9 例，覆盖混合规则、纯域名规则、缺省 `type`、条件规则不放大、默认路由忽略、`geoip:cn` 展开（自带 GeoIPList 编码器）与 inverted 记录报错。

### 遗留（未在本轮实施）

- **A3 直连 DNS 也要能出去**：若 Xray 用公共 DNS 直连解析，那些 53/853 socket 的目标 IP 不在放行集合里，同样被 BLOCK → 域名类直连即便放行 IP 也解析不出来。要么把 Xray DNS 指回 TUN 内 DNS，要么对 `xray.exe` 单独放行 DNS 端口（进程 + 端口，范围可控）。
- **A4 安装规则时把被跳过的直连规则数量打到日志**。现在这个信息完全丢失，用户只能猜。

**5 分钟验证**：在测试机跑 `python -c "from xray_direct import direct_networks,config_path; print(len(direct_networks(config_path())))"`。修复前返回 0 或个位数即证实；修复后应等于 `geoip:cn` 的段数量级（数千）。

## 三、P0-2：看门狗 24 小时硬杀 + 无人重启（解释「跑一天就不通了」）

```python
# mihomo_supervisor.py:413-414（基线）—— 启动看门狗时的参数
"-TimeoutSeconds", "86400",
```

```powershell
# tun-watchdog.ps1:55-90（基线）
$deadline = [DateTimeOffset]::UtcNow.AddSeconds($TimeoutSeconds)
while (...) { ... if ($now -ge $deadline) { break } }
...
if (-not $cancelled -and (Test-ExactProcess -State $state)) {
    Stop-Process -Id ([int]$state.pid) -Force
}
```

核心被杀 → `_monitor` 抛 `SupervisorError` → `run()` 写 `status=failed` → **返回 2 退出**（`mihomo_supervisor.py:206-220`）。没有任何循环重新拉起 supervisor。

所以时间线是：**保护一直开着 + TUN 核心在 24 小时整点被自己人杀掉 + 没有重启 → 物理出站仍被 BLOCK，全机断网**，直到用户手动重开。这与「阶段性不通、重启好一阵」完全吻合，而且周期是**一天一次**，不是随机。

更麻烦的是 `86400` 是**墙上时钟**：笔记本睡一晚，醒来就接近或超过期限，等同于固定在某个时间点自杀。

### 已实施的修复：寿命改成「续期」而不是「处决」

看门狗的职责只有一个：**核心的 supervisor 不再证明自己活着时，把核心停掉**。它没有任何依据去终结一个 supervisor 仍在照看的核心。

`tun-watchdog.ps1`：

- `$TimeoutSeconds` 默认改为 `0`，`<= 0` 表示不设寿命上限。
- 正数仍是「续期窗口」：到期时 `$lifetimeExpired = $true` 退出循环，**不进停止分支**（`-not $lifetimeExpired -and $coreRunning`）。
- 只对**已失去 supervisor 的核心**执行 `Stop-Process`（心跳过期分支）。
- 续期退出时删除自己的 report，避免给仍在运行的核心留下过期结论被后续误读；同时保留 `mihomo-controller-access.json`（核心还活着，GUI 监控还要用它）。
- report 新增 `lifetimeExpired` 与 `coreStillRunning` 两个字段。

`mihomo_supervisor.py`：

- 新增常量 `WATCHDOG_LIFETIME_SECONDS = 0`，随 `-TimeoutSeconds` 传入。
- 抽出 `_watchdog_args()` / `_start_watchdog()`，`_start_core()` 复用。
- `_monitor()` 每轮检查 `self.watchdog.poll()`：核心还在、看门狗却退了 → `_renew_watchdog()` 就地续一个（先写 `checkpoint=watchdog-renewed` 与 `watchdogReason`，再延迟 2 秒，避免秒退的看门狗变成 spawn 循环）。**不动核心、不拆 TUN。**
- `describe_core_exit()` 的 `watchdog-forced-stop` 文案带上原因码与「核心不会自动重启，请 Restart」。

`mihomo-tun.ps1`：

- 失败时除了 checkpoint，再打印 `Reason: <errorMessage>`。基线只打印 `Start failed safely at: <checkpoint>`，而 `watchdog-forced-stop` 恰好只存在于 `errorMessage` 里——这就是「这类故障永远查不出来」的直接原因。

### 如何自证（1 分钟）

看门狗强行停止核心时，`classify_core_exit` 会给出固定原因（`mihomo_supervisor.py:47-58`）：

| reason | 含义 |
|---|---|
| `watchdog-heartbeat-timeout` | 心跳中断（睡眠唤醒后恢复慢）——**修复后唯一会停核心的路径** |
| `watchdog-forced-stop` | 基线里表示「到了寿命期限 / 被取消」，修复后不再出现 |
| `core-clean-exit` / `core-error-exit` | 核心自己退了 |

在 `%LOCALAPPDATA%\v2rayn-tun-controller` 下搜 `watchdog-forced-stop`，若出现且时间点相隔约 24 小时 → 旧版本 P0-2 坐实。

## 四、P0-3：手动模式没有健康监控（未修）

```python
# mihomo_supervisor.py:243-255
if not self.manage_v2rayn:
    relay = self.physical_egress
    if relay and (relay.process is None or relay.process.poll() is not None):
        ...
    time.sleep(3)
    continue
```

`main()` 里 `manage_v2rayn=False` 是硬编码的（`:894`，命令行没有对应开关）。于是：

- 所有 ping 判据、重启授权、`_snapshot` 复核、`_run_connectivity_checks` 全部**不可达**；
- 核心崩了之后也没有任何重启路径（P0-2 修完只解决「看门狗自杀」，核心真的崩了仍然没人拉起来）；
- 而「出站保护」的设计前提是「TUN 一定在」——只要 TUN 不在，物理出站全阻断。

这是整个系统的**最大单点**：一个定时器 + 一个不重启的进程，就能让整机断网。

### 改法（推荐）

在手动模式下补一个**真正的监控循环**，判据参照 macOS 侧已经验证过的那套：

| 观测 | 结论 | 动作 |
|---|---|---|
| TUN 接口在、路由指向它，但走它不通 | `local_tun_path_broken` | 只重建核心/TUN，**不动 v2rayN** |
| 经 1081 的 SOCKS 通、TUN 不通 | `local_tun_path_broken` | 同上 |
| SOCKS 与 TUN 都不通、1081 仍在听 | `node_dead` | 换节点/重连，**仍不必重启 v2rayN** |
| 1081 端口拒绝 | `proxy_stack_down` | 此时才允许碰 v2rayN |
| 只有 ICMP 不通 | **不下结论** | 记录 `icmp_suspect`，不动作 |

## 五、如果真要把 ping 那套打开，先看这三条

`ping_health.py` 现在的判据是：`failures >= 3 and elapsed >= 30s` → 触发重启；`RESTART_COOLDOWN=300`；锁屏时 `restart_consent` 直接给 `locked-auto-restart`（自动批准）。三个问题：

1. **ICMP 在保护下没有放行**：`guard_live.install()` 的 permit 只有 loopback / DHCP / 节点端点 / 直连网段 / TUN 接口过滤；全仓唯一的 ICMP 放行是 `local_access.py:212` 的**局域网** ICMP。公网 ICMP 能否出去取决于 Mihomo TUN 对 echo 的处理，属于实现偶然。
2. **代码自己都写了「尚不能据此断定 TUN 故障」（`:278`），然后照样重启**，`_restart_guarded` 里还有 `self._stop_v2rayn()`（`:322`）——一次误判 = 几十秒全断 + v2rayN 被重启。
3. 冷却 300s + 锁屏自动批准 = **每 5 分钟一次**。

建议：换 HTTP 探针（经 1081 的 204 + 纯 IP 直连 + 两条固定 IP），**2/3 配额**，DNS 单列只作诊断；重启动作分级（见上表）；`locked-auto-restart` 至少要满足「两轮 HTTP 全失败 + SOCKS 也不通」。

## 六、P1：四条会造成「偶发/阶段性」的路径

### 1. 节点解析失败 → 撤销全部放行

`guard_live.py:306-311`：解析异常时 `new_addresses=[]`，随后 `install(refresh=True)` 用空集合重装规则，只剩 loopback/DHCP/直连网段，节点连接全部被阻断，日志写「待确认节点，物理公网默认阻断」（`:326`）。如果这次解析本身要走被阻断的通路（代理或 DoH），就形成自锁。建议：解析失败时**保留上一次有效的 IP 集合**并重试，最多 N 次后才考虑撤权。

### 2. 节点 IP 漂移 + Hysteria 端口跳跃

WFP 只对装配时的 IP/端口放行（`guard_live.py:194-197`）。节点换 A 记录、订阅更新、或 Hysteria `ports` 跳跃到未放行的端口（`mihomo_builder.py:296-299`），都会静默失败。建议：维护「有效 IP/端口集合」（含 TTL），失败时重解析并原子替换；端口跳跃要把整段放行。

### 3. IPv6 静默黑洞

TUN 与规则是 IPv4（`mihomo_builder.py:92,114`），WFP BLOCK 同时覆盖 v4/v6（`guard_live.py:282`）。BLOCK 不发 RST/ICMP unreachable，应用先试 AAAA → 等超时 → 回落 A。建议装一条 `::/0` 黑洞路由（快速失败），或在网卡上禁用 IPv6，并在控制台显式说明「IPv6 被保护层阻断」。

### 4. 持久化规则 + 动态会话规则

WFP sublayer 用 `PERSISTENT` 建（`guard_live.py:183`：`sub.flags = 1`），跨重启保留；而局域网/热点例外是运行期临时加的。watcher 退出后前者还在、后者消失 → 「保护残留但无 owner」，表现为局域网/热点相关功能时好时坏。建议：sublayer 加 owner 标记，启动时校验并接管/清理；动态规则跟随 watcher 生命周期重建。

## 七、P2：可观测性

现在用户能拿到的只有「不通」。缺的是**为什么不通**。两个低成本改进：

1. **60 秒诊断模式**：`FwpmNetEventSubscribe` 订阅 `ALE_AUTH_CONNECT_V4/V6`，输出（进程, 目标 IP, 端口, 命中规则），一次就能回答「这条连接被谁挡了」。
2. **状态从布尔升级为命名结论**：`healthy / local_tun / local_guard / proxy_down / node_dead / dns_hijacked`，每个结论绑定一个动作。这样日志、UI、排障手册三者口径一致。

另外 `guard_live.install()` 是 `clear()` → 逐条 `add_filter`。`geoip:cn` 展开后是数千条 filter，逐条添加有耗时；虽然 `transaction()` 包着，仍建议实机验证刷新窗口内是否真的原子（否则每次网络变化都会短暂全断）。
